# Mounvix M4 — SAF автозагрузка: receipts, Wi‑Fi и состояние WorkManager

**Дата:** 2026-11-19 (Europe/Moscow)
**Статус:** проект для проверки владельцем; код не менялся.
**Основание:** согласованный разговорный дизайн M4 и выбранная миграция старого `last_ms`.

## 1. Цель и границы

Сделать фоновую загрузку медиа из выбранного SAF-дерева повторяемой и восстанавливаемой: один неизменившийся файл на том же сервере/пути не загружается повторно; изменённый или неудачно загруженный файл остаётся доступен для повторной попытки; загрузка не начинается по мобильной сети; интерфейс показывает фактическое состояние WorkManager.

Входит: Android `AutouploadWorker`, планировщик, явная Room-миграция, SAF-метаданные и URI-доступ, статус автозагрузки и проверки. Не входит: переписывание ручной загрузки, серверная синхронизация файлов в обе стороны, хеширование каждого исходного файла, OAuth/rclone, изменение формата Android-релиза.

## 2. Текущее состояние

- Worker собирает максимум 500 медиафайлов до фильтрации и выбирает их по единому `autoupload_last_ms`; одинаковые файлы могут загружаться повторно или старые файлы — пропускаться после ошибки.
- В планировщике стоит `NetworkType.CONNECTED`; отдельной проверки транспорта Wi‑Fi перед каждым файлом нет.
- Успешная загрузка обновляет только глобальный watermark и строковый статус в `SharedPreferences`; ошибки не образуют записей для per-file retry.
- Экран читает статус один раз, а не наблюдает состояние WorkManager.
- Room DB версии 1 хранит `favorites`/`recents` и использует `fallbackToDestructiveMigration()`. Новую таблицу нельзя добавлять с риском удалить эти пользовательские данные.

## 3. Модель receipt

Room v2 добавляет `autoupload_receipts` с уникальным ключом `tree_key + document_key + destination_key` и полями `size_bytes`, `modified_ms`, `relative_path`, `uploaded_at_ms`; `autoupload_attempts` с тем же ключом хранит `attempt_count`, `next_retry_ms` и безопасный класс ошибки; `autoupload_legacy_cutoffs` связывает tree/destination с `cutoff_ms`; `autoupload_run_state` хранит последнее terminal outcome, время, счётчики и безопасный error class по tree/destination без секретов. `document_key` — SHA-256 digest от authority SAF-провайдера и `DocumentsContract.getDocumentId(uri)`; raw document ID и полный content URI в БД не сохраняются. `tree_key` — SHA-256 от нормализованного URI SAF-дерева. Размер/mtime/относительный путь описывают версию файла.

`destination_key` отделяет receipt от другого сервера, удалённого профиля или каталога назначения. Он строится как SHA-256 от типа адаптера, стабильного несекретного root identity, account/user ID и нормализованного каталога назначения; пароль и токены в ключ не входят. Если получателя меняют, старый receipt не должен ошибочно блокировать загрузку на новый адрес. Для новых файлов destination сохраняет относительную структуру SAF-дерева внутри выбранного каталога (`destDir/<relative path>`); root-level файлы сохраняют прежний путь, а одинаковые имена в разных подпапках больше не перезаписывают друг друга. `relative_path` формируется из отдельных provider names, нормализуется и отклоняет пустые/`.`/`..`/разделители внутри сегмента. Перед PUT адаптер создаёт недостающие родительские каталоги; если это невозможно, upload завершается ошибкой без receipt.

Успешный receipt создаётся только после подтверждённого полного завершения загрузки. Перед передачей фиксируются metadata; после передачи metadata запрашиваются повторно. Если документ изменился во время передачи, receipt для старой версии не создаётся. При ошибке, отмене, недоступном SAF URI или неизвестной идентичности/metadata receipt не создаётся — файл остаётся кандидатом на повтор.

## 4. Миграция v0.1.3 → новая версия

Владелец выбрал сохранять прежнюю границу, чтобы не инициировать массовую повторную загрузку при первом запуске. При Room-миграции из v1:

1. Сохранить `autoupload_last_ms` вместе с идентификаторами **дерева и получателя, выбранных на момент миграции**, в `autoupload_legacy_cutoffs`.
2. Для этой пары tree/destination файлы с `modified_ms <= cutoff_ms` и без receipt считаются историческими и не загружаются повторно. Граница не применяется к новому SAF-дереву или другому серверу/каталогу назначения. Если прежнюю идентичность получателя нельзя восстановить однозначно, cutoff не привязывается к неизвестному получателю; UI сообщает, что при первом запуске возможна повторная загрузка.
3. Если на момент миграции нет сохранённого дерева или валидного положительного watermark, legacy cutoff не создаётся.
4. Новый алгоритм больше не использует глобальный `last_ms` как фильтр для всех деревьев. Старый ключ можно оставить для диагностики/совместимости, но он не должен снова стать глобальной границей.

Это намеренно сохраняет возможный старый пропуск: если v0.1.3 уже продвинул watermark поверх неудачного файла, файл до cutoff может остаться незагруженным. Это известный и принятый компромисс. Для Room обязателен явный `Migration(1, 2)` и тест сохранения `favorites`/`recents`; destructive fallback для этой миграции удаляется. Если таблица cursor Android Advanced Mode попадёт в тот же релиз, её добавляют в эту же migration; при более позднем релизе добавляют следующую forward migration. Неизвестная версия БД должна завершаться безопасной понятной ошибкой, а не молча очищать пользовательские таблицы.

## 5. Алгоритм и сеть

1. Worker проверяет разрешение выбранного SAF дерева, настройки и доступность получателя.
2. Worker делает metadata-only обход SAF-дерева; на каждой записи до лимита партии сверяет media-тип, `tree_key`, `document_key`, metadata, legacy cutoff, receipt и retry backoff. Из подходящих записей он набирает максимум 500 eligible-кандидатов (а не первые 500 сырых записей), после чего сортирует их по `modified_ms`, затем `document_key`.
3. Worker пытается обработать всю собранную партию. Неудачная попытка записывает `attempt_count` и `next_retry_ms` с capped exponential backoff (1 минута → максимум 24 часа); до `next_retry_ms` файл пропускается, поэтому постоянная ошибка не блокирует следующие записи. После успеха attempt-row удаляется. Повторное сканирование начинает с корня, пропускает receipts/backoff и доходит до следующих кандидатов; при отмене незапущенные элементы остаются доступны в следующем run.
4. Перед любой сетевой операцией и непосредственно перед открытием/отправкой **каждого** файла `ConnectivityManager` проверяет активный транспорт на `TRANSPORT_WIFI`; `ACCESS_NETWORK_STATE` добавляется в manifest. `NetworkType.CONNECTED` остаётся только условием запуска WorkManager и не считается Wi‑Fi-проверкой (Ethernet также не принимается).
5. Во время передачи регистрируется `NetworkCallback`. При потере Wi‑Fi/смене активного транспорта autoupload отменяет текущий запрос/закрывает адаптерный поток, не открывает следующий файл и не создаёт receipt. `StorageSource` получает cancellable-upload путь для WebDAV/SMB/SFTP; ручная загрузка не меняется. На мобильной сети ни новые соединения, ни последующие чанки файла не отправляются.
6. При отсутствии Wi‑Fi periodic worker выставляет `WAITING_FOR_WIFI` и завершает этот периодический запуск без сетевого I/O; следующая периодическая проверка повторит работу. Явный Run Now остаётся отложенным через WorkManager backoff. Уже завершённые receipts сохраняются; прерванный файл остаётся кандидатом на повтор.
7. Для локального сервера разрешено Wi‑Fi-подключение без требования `NET_CAPABILITY_VALIDATED`: изолированная LAN может быть доступна без общего интернета. Фактическая отправка должна завершиться штатным успехом получателя.

Worker продолжает использовать уникальные periodic и Run Now-задачи; конкурентные одинаковые запуски не должны создавать дублирующие uploads. Для каждого файла worker сохраняет receipt атомарно только после подтверждения источника загрузки.

## 6. Статус UI

Экран автозагрузки наблюдает `WorkManager.getWorkInfosForUniqueWorkFlow(...)` для текущего ENQUEUED/RUNNING состояния и `autoupload_run_state` Flow для последнего terminal результата выбранной tree/destination. Он показывает ожидающее/выполняющееся/ожидающее Wi‑Fi/успешное/ошибочное/отменённое состояние, число выполненных/ошибочных файлов и время последнего завершения. Worker публикует текущий прогресс через `WorkInfo.progress` и атомарно сохраняет terminal summary в Room; устаревшие preferences не могут перезаписать текущую работу.

Существующие кнопки «включить/выключить» и «запустить сейчас» сохраняют смысл. При отсутствии выбранного дерева, постоянного разрешения SAF или получателя UI должен указывать конкретное действие, а не показывать фиктивный успех.

## 7. Проверки и критерии приёмки

- Room migration v1→v2 сохраняет favorites/recents, переносит legacy cutoff ровно к ранее выбранному дереву и не переносит его на другое дерево.
- Неизменившиеся `(tree, documentId, size, mtime, destination)` пропускаются; изменение size, mtime, пути назначения или получателя делает файл кандидатом.
- Receipt создаётся только после успешного upload; ошибка, отмена и изменение файла во время передачи оставляют файл для retry.
- Wi‑Fi проверяется перед каждым файлом; переключение Wi‑Fi→cellular между файлами блокирует следующий файл, а переключение во время файла отменяет дальнейшую передачу чанков/запрос; ни один такой файл не получает receipt.
- Более 500 файлов не приводят к вечному ограничению первыми 500 уже известных записей; ошибки одного файла не скрывают последующие; два одноимённых файла из разных SAF-подпапок получают разные destination paths.
- UI объединяет живой WorkManager Flow и Room last-run Flow; переход ENQUEUED/RUNNING→terminal отображается без перезапуска экрана, а последний terminal summary переживает process death.
- Тесты покрывают planner/receipt matching, Room migration, cutoff/tree scoping, retry, Wi‑Fi loss between files and during transfer, adapter cancellation и status observation; emulator QA проверяет настоящий SAF picker, сохранённое URI-разрешение, Wi‑Fi guard и удалённый файл.

## 8. Не входит

- Контентное хеширование для обнаружения изменений при неизменных size/mtime; эта метрика остаётся согласованным компромиссом.
- Перенос прежних пропущенных файлов до legacy cutoff; массовая миграционная переотправка намеренно не выполняется. Старые файлы, ранее записанные в плоский destination, автоматически не перемещаются и не удаляются; M4 остаётся неразрушающим и не выполняет sync/delete.
- Новый push relay/FCM и изменения серверного binary.
